# AiCare PPT 발표 스크립트

안녕하십니까. 서버비얼마나오조의 팀장이자 발표를 맡은 김태빈입니다.

발표는 팀 소개, 프로젝트 선정 배경, 서비스 및 주요 기능, 담당 영역별 구현 내용과 트러블슈팅, 마지막으로 향후 발전 방향과 느낀 점 순서로 진행하겠습니다.

먼저 팀 소개입니다. 저희 팀은 프로젝트 매니저, 개발, 인프라, 모니터링, 데이터베이스, CI/CD 담당으로 역할을 나누어 프로젝트를 진행했습니다. 단순히 기능을 구현하는 데 그치지 않고, 실제 서비스 운영을 고려하여 아키텍처 설계, 보안, 자동화, 모니터링까지 함께 구축했습니다.

AiCare는 영유아 보호자가 아이의 증상과 건강 상태를 입력하면, AI가 이를 분석하여 증상을 체계적으로 정리하고 적절한 진료 방향을 안내하는 스마트 헬스케어 서비스입니다. 의료 지식이 부족한 보호자도 아이의 상태를 쉽게 파악하고 더 빠르게 대응할 수 있도록 지원하는 것을 목표로 했습니다.

다음은 프로젝트 선정 배경입니다.

첫 번째 배경은 육아 데이터의 활용성 부족입니다. 보호자들은 육아일기, 예방접종 기록, 성장 정보, 증상 기록 등 다양한 데이터를 지속적으로 남기고 있습니다. 하지만 이러한 정보는 대부분 단순 기록으로만 저장되고, 실제 건강 관리에는 적극적으로 활용되지 못하고 있습니다. 저희는 이 데이터를 AI와 결합하면 더 의미 있는 건강 정보로 활용할 수 있다고 판단했습니다.

두 번째 배경은 영유아 의료 정보 접근성 문제입니다. 최근 소아청소년과 전공의 확보율 감소와 일부 지역의 소아과 부족 현상으로 인해, 보호자들은 의료 정보를 얻기 위해 인터넷 검색이나 온라인 커뮤니티에 의존하는 경우가 많습니다. 하지만 검증되지 않은 정보도 많기 때문에 어떤 내용을 신뢰해야 할지 판단하기 어렵습니다. 저희는 AI를 통해 아이의 상태를 분석하고 필요한 정보를 한 곳에서 제공하는 서비스를 기획했습니다.

세 번째 배경은 AI 활용 문화의 확산입니다. 최근에는 검색 엔진보다 AI에게 직접 질문하여 답을 얻는 방식이 빠르게 보편화되고 있습니다. 특히 건강과 육아 분야에서는 자신의 상황을 자연어로 설명하고 맞춤형 정보를 얻고자 하는 수요가 증가하고 있습니다. 이러한 변화에 맞춰 AI 기반 영유아 건강 관리 서비스를 기획하게 되었습니다.

이러한 문제를 해결하기 위해 저희는 영유아 건강 데이터를 기록하고 관리하며, AI가 이를 분석하여 필요한 정보를 제공하는 AiCare를 개발했습니다.

다음은 서비스 흐름입니다. 사용자가 증상을 입력하면 서비스는 입력 문장을 분석합니다. 이후 형태소 분석과 AI 모델을 활용해 핵심 증상 키워드를 추출하고, 아이의 상태를 종합적으로 분석합니다. 분석 결과를 기반으로 적절한 진료 방향을 안내하며, 사용자는 관련 병원 정보와 진료 정보를 확인할 수 있습니다.

주요 기능은 회원 관리, 아이 정보 관리, 증상 분석, 병원 검색, 병원 리뷰, 병원 및 기록 조회로 구성했습니다. 보호자는 아이 정보를 등록하고 증상을 입력한 뒤 AI 분석 결과와 추천 병원 정보를 확인할 수 있습니다.

기술 스택은 프론트엔드, 백엔드, 인프라, 데이터베이스, 모니터링, CI/CD 영역으로 구성했습니다. 백엔드는 MSA 구조로 설계하여 기능별 책임을 분리했고, 인프라는 AWS EKS 기반으로 구축했습니다. 데이터베이스는 PostgreSQL을 사용했으며, Terraform을 통해 인프라를 코드로 관리했습니다. 모니터링은 Prometheus, Grafana, Loki, Slack 연동을 활용했고, GitHub Actions와 ArgoCD를 통해 CI/CD 환경을 구축했습니다.

## 인프라 파트 1

안녕하십니까. 인프라 파트에서 EKS와 Terraform 기반 인프라 관리를 담당한 강지윤입니다. 지금부터 AiCare 서비스의 인프라 아키텍처와 주요 기술 선택 이유를 설명드리겠습니다.

먼저 인프라 전체 아키텍처입니다. 전체 구조는 AWS Cloud 영역과 On-Prem 영역으로 나누어 설계했습니다. 사용자의 요청은 ALB를 통해 EKS 클러스터로 전달되고, 각 마이크로서비스가 요청을 처리합니다.

일반 서비스 데이터는 AWS RDS에 저장되지만, 민감한 의료 데이터는 AWS 내부에 직접 저장하지 않고 VPN으로 연결된 On-Prem 환경의 FastAPI 서버를 거쳐 별도 PostgreSQL에 저장되도록 분리했습니다. 이를 통해 클라우드의 운영 편의성과 민감정보 보호를 동시에 확보하고자 했습니다.

이러한 구조를 설계할 때 저희는 다섯 가지 기준을 중심으로 판단했습니다. 첫 번째는 가용성입니다. Multi-AZ 기반 구성으로 장애 발생 시 서비스 중단을 최소화했습니다. 두 번째는 확장성입니다. MSA 구조 특성상 서비스별 독립 확장이 가능해야 했습니다. 세 번째는 민감정보 보호입니다. 의료 데이터는 일반 데이터보다 더 높은 수준의 보호가 필요했습니다. 네 번째는 배포 자동화, 다섯 번째는 비용 효율성입니다. 운영 부담은 줄이고 필요한 만큼만 리소스를 사용하도록 설계했습니다.

기술 선택의 기준은 우리 서비스 요구사항에 얼마나 적합한가였습니다. 컨테이너 오케스트레이션은 EKS, 로드밸런싱은 ALB, IaC는 Terraform을 선택했습니다. 또한 데이터는 중요도에 따라 AWS와 On-Prem으로 분리 저장했고, ArgoCD 기반 GitOps 배포와 HPA, Karpenter 기반 Auto Scaling 구조를 적용했습니다.

다만 이러한 구조에도 trade-off는 존재했습니다. 첫 번째는 운영 복잡도 증가입니다. EKS, VPN, On-Prem 환경이 함께 존재하면서 관리 포인트가 늘어났습니다. 두 번째는 VPN 장애 가능성입니다. 단일 VPN 경로에 장애가 발생하면 민감 데이터 처리에 영향이 갈 수 있습니다. 세 번째는 비용 관리 필요성입니다. ALB, EKS, NAT Gateway 등 지속 비용이 발생하기 때문입니다. 이를 완화하기 위해 Terraform 기반 표준화, 모니터링, Auto Scaling을 적용했습니다.

컨테이너 플랫폼으로는 ECS와 EKS를 비교했습니다. ECS는 운영이 단순하다는 장점이 있지만, 저희 서비스는 MSA 구조이고 향후 서비스 수가 증가할 가능성이 높다고 판단했습니다. 특히 서비스별 독립 배포와 Pod 단위 제어, Kubernetes ecosystem 활용이 중요했습니다. 그래서 초기 구축 난이도가 더 높더라도 장기적인 확장성과 유연성을 고려해 EKS를 선택했습니다.

IaC 도구는 CloudFormation과 Terraform을 비교했습니다. CloudFormation은 AWS 환경에 최적화되어 있지만, 저희는 AWS뿐 아니라 Kubernetes와 Helm까지 함께 관리해야 했습니다. Terraform은 다양한 provider를 통해 여러 환경을 하나의 코드베이스에서 관리할 수 있다는 장점이 있었고, 모듈화를 통한 협업에도 유리했습니다.

Terraform 모듈화는 재사용성, 관심사 분리, 유지보수성, 협업 효율을 기준으로 적용했습니다. 공통 모듈을 분리하여 환경이 달라져도 동일한 인프라 구성을 반복적으로 사용할 수 있도록 했고, 네트워크, 보안, EKS 등 역할별로 리소스를 분리해 관리하도록 구성했습니다. 이를 통해 변경 범위를 최소화하고 팀원 간 작업 충돌을 줄일 수 있었습니다.

Auto Scaling은 Pod 레벨과 Node 레벨에서 각각 확장되는 2단계 구조로 구성했습니다. 트래픽이 증가하면 먼저 HPA가 Pod 수를 늘려 서비스 처리량을 확장합니다. 이후 Pod 증가로 Node 리소스가 부족해지면 Karpenter가 새로운 Worker Node를 자동으로 추가합니다. 이를 통해 트래픽 변화에 유연하게 대응하면서 필요한 시점에만 리소스를 확장해 운영 효율성을 높일 수 있었습니다.

## 인프라 파트 2

다음으로 구현 및 검증 내용을 설명드리겠습니다. 검증은 단순히 화면이 정상적으로 보이는지만 확인한 것이 아니라, 사용자 요청이 Frontend에서 시작해 ALB, EKS의 Backend MSA, RDS와 On-Prem 저장소까지 이어지는 실제 요청 흐름을 기준으로 진행했습니다.

먼저 Frontend 영역입니다. Frontend는 Vite 기반으로 사용자 화면을 구현했으며, 슬라이드에는 문진 입력 페이지를 예시로 가져왔습니다. 사용자는 아이를 선택하고 증상을 자연어로 입력한 뒤 AI 분석을 요청할 수 있습니다.

제가 확인한 부분은 세 가지입니다. 첫째, 아이 선택과 증상 입력이 정상적으로 동작하는지 확인했습니다. 둘째, 서비스별 API Client를 통해 Backend API 요청이 정상적으로 전달되는지 확인했습니다. 셋째, 배포된 ALB 환경에서 응답과 오류가 정상적으로 처리되는지 검증했습니다. 즉, Frontend/App 영역에서는 사용자 화면 구현과 실제 배포 환경에서의 API 연동을 중심으로 확인했습니다.

다음은 Backend 영역입니다. Backend는 기능별 책임을 분리하기 위해 Auth/User, Questionnaire, AI Triage, Board, Hospital 서비스로 나누었습니다. 이렇게 구성한 이유는 기능별 독립 배포와 확장이 가능하고, 특정 서비스 장애가 전체 서비스로 확산되는 것을 줄이기 위해서입니다.

예를 들어 AI 분석 서비스에 문제가 생기더라도 회원 인증이나 정보공유 게시판 기능까지 함께 영향을 받지 않도록 책임을 분리했습니다. 서비스 흐름은 Frontend 요청이 ALB를 거쳐 Backend MSA로 들어오고, 경로에 따라 각 서비스로 라우팅되는 구조입니다.

데이터 저장은 성격에 따라 분리했습니다. 회원 계정 메타데이터나 게시글 같은 일반 서비스 데이터는 AWS RDS에 저장하고, 아이 식별정보와 문진 원문 같은 민감정보는 On-Prem FastAPI를 거쳐 암호화 후 On-Prem DB에 저장하도록 구성했습니다. 비밀번호는 복호화가 필요 없기 때문에 scrypt 단방향 해시를 사용했고, 아이 정보와 문진 원문은 다시 조회가 필요하기 때문에 Fernet 기반의 복호화 가능한 암호화를 적용했습니다.

다음은 Hybrid Network 연결 방식 비교입니다. 앞에서 설명드린 것처럼 저희는 민감정보를 On-Prem 영역으로 분리 저장하는 구조를 선택했기 때문에, AWS와 On-Prem을 어떤 방식으로 연결할지 비교했습니다.

VPC Peering은 AWS VPC 간 연결에는 단순하지만, 실제 On-Prem IPsec VPN 구조를 검증하기에는 적합하지 않았습니다. 전용 VPN 장비는 운영 환경에 가장 가깝고 안정적이지만, 장비 비용과 구축 시간이 프로젝트 환경에서는 부담이 있었습니다. 그래서 EC2를 Software Customer Gateway처럼 활용할 수 있는 strongSwan EC2를 선택했습니다.

strongSwan EC2는 실제 장비 없이도 AWS Site-to-Site VPN과 IPsec 터널을 구성할 수 있어, 비용과 실습 가능성 측면에서 가장 적합하다고 판단했습니다. 다만 EC2 기반이기 때문에 단일 장애점이 될 수 있어, 향후에는 이중화나 BGP 기반 구성이 필요합니다.

마지막으로 Backend Pod의 IRSA 권한 불일치 트러블슈팅입니다. Pod는 정상 실행 중이었지만, Bedrock 호출 권한을 가져오지 못해 AI 분석 API에서 502 또는 500 오류가 발생했습니다. 원인은 Backend Pod의 ServiceAccount와 IAM Role 매핑이 일치하지 않았기 때문이었습니다. 이를 수정한 뒤 Bedrock 호출과 AI 분석 API가 정상 동작하는 것을 확인했습니다.

이 문제를 통해 Pod Running 상태와 AWS 권한 정상 여부는 별개이며, AWS 서비스 연동 시에는 IRSA 설정까지 함께 확인해야 한다는 점을 알 수 있었습니다.

## 개발 파트

다음은 제가 담당한 개발 파트입니다. 개발 파트에서는 AI 기반 증상 분석과 병원 검색 기능 구현을 담당했습니다. 핵심 목표는 사용자가 입력한 자연어 문장을 서비스가 이해할 수 있는 증상 정보로 변환하고, 이를 병원 추천까지 연결하는 것이었습니다.

사용자는 "아이가 열이 나고 기침을 계속해요"와 같이 일상적인 문장으로 증상을 입력합니다. 따라서 입력 문장에서 핵심 증상 키워드를 추출하는 과정이 필요했습니다.

먼저 전체 아키텍처를 설명드리겠습니다. 사용자의 요청은 CloudFront와 ALB를 거쳐 AWS EKS 환경으로 전달됩니다. 문진 정보는 questionnaire-service에서 수집되고, SQS를 통해 ai-triage-service로 전달됩니다. ai-triage-service에서는 형태소 분석을 수행하여 핵심 증상 키워드를 추출하고, 이후 AWS Bedrock 모델을 호출하여 문장 전체의 의미를 분석합니다.

분석 결과는 Amazon RDS와 S3에 저장되며, 필요한 경우 VPN을 통해 On-Prem 환경의 FastAPI 서버와 PostgreSQL과도 연동됩니다. 즉, 사용자가 입력한 자연어가 AI 분석 과정을 거쳐 증상 분석과 병원 추천까지 연결되는 구조로 설계했습니다.

다음은 형태소 분석기 비교입니다. 사용자가 입력하는 증상 문장은 대부분 짧고 구어체 표현이 많기 때문에, 단순 문자열 검색만으로는 정확한 증상 키워드를 추출하기 어렵습니다. 그래서 저희는 KIWI와 OKT를 비교했습니다.

OKT는 SNS 분석과 감성 분석 분야에서 많이 활용되는 형태소 분석기로, 일반적인 한국어 문장 분석에서 안정적인 성능을 제공합니다. 특히 구어체 표현이나 일상적인 문장을 다루는 데 장점이 있습니다. 반면 KIWI는 복합 명사 처리와 띄어쓰기 오류 처리에 강점이 있고, 사용자 사전 확장이 용이하다는 장점이 있습니다. 이러한 특성은 열, 기침, 콧물, 구토와 같은 의료 증상 키워드를 추출하는 데 적합하다고 판단했습니다.

운영 환경 측면에서도 차이가 있었습니다. OKT는 KoNLPy 기반으로 동작하기 때문에 JVM 설정이 필요했고, Docker와 Kubernetes 환경에서는 추가적인 Java 의존성 구성이 필요했습니다. 반면 KIWI는 운영 환경 구성 측면에서 상대적으로 부담이 적었습니다.

실제 형태소 분석 결과를 보면, 예시 문장 "아기가 어젯밤부터 열이 나고 콧물이 계속 나와요"에서 KIWI는 열, 콧물과 같은 증상 키워드를 정확하게 분리하여 추출했습니다. 반면 OKT는 일부 단어를 명사로 처리하거나 잘못 분리하는 결과가 나타났습니다. 따라서 저희는 분석 정확도, 사용자 사전 확장성, 운영 환경의 안정성을 종합적으로 고려하여 최종적으로 KIWI를 선택했습니다.

하지만 형태소 분석만으로는 문장 전체의 의미를 이해하는 데 한계가 있었습니다. 예를 들어 같은 발열 증상이라도 기침, 콧물, 구토와 같은 동반 증상에 따라 추천 방향이 달라질 수 있습니다. 그래서 이러한 문맥 정보를 함께 분석하기 위해 AWS Bedrock 기반 Claude 모델을 적용했습니다.

모델 선정 과정에서는 Claude Sonnet 4.5와 Claude Haiku 4.5를 비교했습니다. 두 모델 모두 최대 컨텍스트는 20만 토큰으로 동일하지만, 토큰 단가에는 차이가 있습니다. Claude Haiku 4.5는 입력 토큰 비용이 100만 토큰당 약 1달러, 출력 토큰 비용이 100만 토큰당 약 5달러입니다. 반면 Claude Sonnet 4.5는 입력 토큰 비용이 100만 토큰당 약 3달러, 출력 토큰 비용이 100만 토큰당 약 15달러입니다. 즉, Sonnet은 Haiku보다 입력과 출력 모두 약 3배 높은 비용이 발생합니다.

실측 기준으로는 Haiku가 요청 1회당 약 350토큰, Sonnet이 요청 1회당 약 330토큰을 사용했습니다. 입력 토큰과 출력 토큰을 별도로 측정한 것은 아니기 때문에, 비용 계산에서는 입력 70%, 출력 30%라는 가정을 적용했습니다. 이 기준으로 계산하면 Haiku는 요청 1회당 약 0.00077달러, Sonnet은 요청 1회당 약 0.002178달러가 발생합니다. 이를 10,000회 요청 기준으로 환산하면 Haiku는 약 7.7달러, Sonnet은 약 21.78달러입니다.

또한 동일한 소아 문진 시나리오를 대상으로 반복 테스트를 수행했습니다. 총 3개의 문진 시나리오를 각 모델별 10회씩 수행하여 총 30회의 테스트를 진행했습니다. 테스트 결과 Sonnet 4.5의 평균 응답시간은 약 8.9초, Haiku 4.5는 약 4.2초로 측정되었습니다. 결과적으로 Haiku 4.5가 Sonnet 4.5 대비 약 53% 빠른 응답 성능을 보였고, 빠른 추가 문진 질문 생성이 중요한 저희 서비스에 더 적합하다고 판단하여 Claude Haiku 4.5를 최종 모델로 선정했습니다.

마지막으로 병원 검색 기능입니다. 사용자가 진료과와 지역 정보를 입력하면 먼저 검색어를 정규화하여 검색 정확도를 높였습니다. 이후 Kakao REST API를 호출하여 해당 조건에 맞는 병원 정보를 조회합니다. 또한 병원 정보의 활용성을 높이기 위해 카카오 API에서 조회한 병원명과 주소를 기반으로 Google Places API를 추가 호출하여 영업시간 정보를 보강했습니다. 최종적으로 사용자는 병원명, 위치, 운영시간, 전화번호 등의 정보를 한 화면에서 확인할 수 있도록 구현했습니다.

## 데이터베이스 파트

안녕하십니까. 이번 프로젝트에서 데이터베이스 설계를 담당한 신예원입니다.

먼저 DBMS 선정 과정입니다. 저희는 MongoDB, MySQL, PostgreSQL을 두고 비즈니스 요구사항에 따른 적합성을 평가했습니다.

MongoDB는 스키마가 자유로운 구조로 초기 생산성이 높고 확장성이 뛰어나다는 장점이 있습니다. 하지만 저희 서비스는 사용자, 자녀, 문진, AI 분석 결과처럼 관계가 중요한 데이터가 많아 정합성 관리가 어렵다는 한계가 있었습니다.

MySQL은 전통적인 OLTP 환경에 유리하지만, 대규모 조인 시 병목 우려가 있고 AI 분석 데이터처럼 반정형 JSON 데이터를 저장하고 조회하는 데에는 아쉬움이 있었습니다.

반면 PostgreSQL은 RDBMS의 엄격한 스키마 무결성을 유지하면서도 JSONB 타입과 GIN 인덱스를 통해 AI 결과물까지 효율적으로 처리할 수 있습니다. 따라서 저희 서비스의 요구사항을 가장 균형 있게 충족한다고 판단하여 PostgreSQL을 최종 채택했습니다.

다음은 ERD 구조입니다. 먼저 모든 테이블에 단일 UUID 인공키를 적용했습니다. 이를 통해 복합키 사용 시 발생할 수 있는 부분 함수 종속성을 제거하고, 제2정규화를 구조적으로 만족시켰습니다. 이후 일반 컬럼 간의 이행적 함수 종속성을 끊어내는 제3정규화를 적용했습니다.

구체적으로 consultations 테이블에서 대용량 AI 분석 결과물인 ai_results를 별도 테이블로 분리했고, S3 리포트 경로 자산 또한 consultation_assets로 독립시켰습니다. 이를 통해 데이터 모델은 중복 없이 최적화되었고, 온프레미스 환경에도 핵심 민감정보 테이블 구조를 안정적으로 구성할 수 있었습니다.

UUID를 사용한 이유는 크게 세 가지입니다. 첫 번째는 하이브리드 분리 DB 환경에서의 ID 충돌 방지입니다. 일반적인 Auto Increment 방식은 각 DB에서 1번, 2번처럼 순차적으로 ID가 생성되기 때문에, 클라우드 DB와 온프레미스 DB를 함께 사용할 경우 ID가 겹칠 수 있습니다. 반면 UUID는 고유한 문자열을 생성하기 때문에 서로 다른 DB에서 생성하더라도 충돌 가능성을 줄일 수 있습니다.

두 번째는 보안성 강화입니다. 숫자 ID가 주소나 API 요청에 노출되면 사용자가 숫자를 바꾸어 다른 데이터에 접근을 시도하는 무작위 대입 공격에 취약할 수 있습니다. UUID는 예측하기 어려운 값이기 때문에 이러한 위험을 줄이는 데 도움이 됩니다.

세 번째는 개발 편의성입니다. 순차적 숫자 ID는 데이터가 DB에 저장되는 순간에 발급되지만, UUID는 애플리케이션 단에서 미리 생성할 수 있습니다. 따라서 AI 분석 서버와 통신하거나 임시 데이터를 처리할 때 더 유연한 개발 흐름을 만들 수 있었습니다.

마지막으로 실제 환경 검증입니다. 설계된 데이터 구조가 실제 인프라 환경에서 일치하는지 확인하기 위해 AWS SSM 보안 터널링을 구축하여 원격 접속을 수행했습니다. 로컬 테스트 서버 내부망에 구성된 PostgreSQL 엔진에 접속하여 users를 포함한 핵심 서비스 테이블 릴레이션을 확인했고, 프라이빗 서브넷에 격리된 RDS 인스턴스에도 SSM 터널을 통해 접속하여 민감정보 테이블을 검증했습니다. 이를 통해 하이브리드 환경 간 스키마 정합성이 일치함을 확인할 수 있었습니다.

## CI/CD 파트

안녕하십니까. 프로그램 배포 및 운영 자동화 시스템 구축 사례를 발표할 OOO입니다.

저희가 구축한 시스템은 개발자가 작성한 소스 코드가 서버에 반영되기까지의 전 과정을 자동화하는 구조입니다. 코드가 수정되면 시스템이 이를 감지하고, 자동으로 빌드와 검증을 수행한 뒤 실제 운영 서버에 안전하게 반영하도록 설계했습니다.

이 시스템을 도입한 배경은 저희 운영 환경의 특수성 때문입니다. 저희는 시스템을 매일 새로 구성하고 다시 배포해야 하는 환경이었습니다. 매번 사람이 접속해서 수동으로 관리하는 방식은 시간이 오래 걸릴 뿐만 아니라, 작업자마다 설정이 달라져 오류가 발생할 가능성도 높았습니다. 이를 해결하기 위해 반복 작업을 규격화하고, 시스템이 스스로 설계된 원본 상태를 유지하도록 제어하는 자동화 방식을 채택했습니다.

수동 방식과 자동화 방식의 처리 속도를 비교한 결과, 기존 방식은 단계마다 작업자가 개입하고 대기해야 하므로 지연이 발생했습니다. 반면 자동화 시스템을 적용한 뒤에는 배포 리드 타임을 크게 단축할 수 있었습니다. 또한 작업자의 대기 시간이 줄어들었고, 시스템이 항상 안정적인 최신 상태를 유지하도록 관리할 수 있었습니다.

자동화를 구축하는 과정에서는 두 가지 주요 문제가 있었습니다. 첫 번째는 권한 문제입니다. 자동화 프로그램이 서버 배포 설정을 직접 수정해야 했지만, 기본 보안 설정상 읽기 권한만 있어 수정 단계에서 거부 오류가 발생했습니다. 이를 해결하기 위해 쓰기 권한을 명시적으로 부여하는 설정으로 변경했습니다.

두 번째는 무한 반복 오류입니다. 권한을 열어주자 프로그램이 자신이 수정한 설정 변경을 새로운 작업 지시로 인식하여, 작업을 반복 실행하는 문제가 발생했습니다. 이를 해결하기 위해 자동화 프로그램이 스스로 수정한 내역에 대해서는 다음 작업을 실행하지 않고 건너뛰도록 규칙을 추가했습니다. 이 두 가지 설정을 통해 사람의 개입이 필요 없는 자동화 흐름을 완성했습니다.

현재 모든 배포 작업은 오류 없이 자동으로 연동되고 있습니다. 또한 비밀번호나 인증 키 같은 민감한 정보가 외부 저장소에 노출되지 않도록 격리 설정을 적용하여 관리하고 있습니다. 향후에는 보안 관리 전용 자동화 도구를 추가로 결합하여 안전성을 더 높일 계획입니다.

## 마무리

마지막으로 AiCare의 향후 발전 방향에 대해 말씀드리겠습니다.

현재 AiCare는 보호자가 아이의 증상을 입력하면 AI가 이를 분석하여 문진 정보를 제공하고 병원 정보를 안내하는 단계까지 구현되어 있습니다. 향후에는 이러한 문진 정보를 실제 의료 서비스와 연결하여 더 실질적인 도움을 제공하는 방향으로 발전시키고자 합니다.

먼저 AI가 생성한 문진 결과를 기반으로 증상에 적합한 전문의를 추천하는 의사 매칭 기능을 추가할 계획입니다. 이를 통해 보호자는 여러 정보를 직접 검색하지 않아도 아이의 상태에 적합한 의료진을 더 쉽게 찾을 수 있습니다.

다음으로는 비대면 진료 기능입니다. 기존에 작성된 문진 정보를 의료진에게 전달하여 진료 준비 시간을 단축하고, 더 효율적인 상담이 가능하도록 발전시킬 예정입니다.

또한 진료 결과와 연계한 전자처방 기능을 도입하여 병원 방문이 어려운 상황에서도 편리하게 의료 서비스를 이용할 수 있도록 하고자 합니다.
